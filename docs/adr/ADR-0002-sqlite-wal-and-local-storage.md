# ADR-0002: اعتماد قاعدة بيانات SQLite بنمط WAL والتخزين المحلي

## الحالة (Status)
معتمد (Accepted)

## السياق (Context)
تحتاج المنظومة لتخزين سجلات الكواشف، أجهزة الفحص، المصادر المشعة، قياسات الفحص الخماسية، لقطات الاعتماد (Snapshots)، وسجل التدقيق الأمني (Audit Log). يجب أن تكون قاعدة البيانات مدمجة وخفيفة ولا تتطلب خادماً خارجياً (Serverless) مع ضمان سلامة البيانات من التلف عند انقطاع التيار الكهربائي المفاجئ في المعمل.

## القرار (Decision)
اعتماد محرك **SQLite 3** كقاعدة بيانات محلية متكاملة، مع التكوين الإلزامي التالي:
1. تفعيل القيود المرجعية الصارمة: `PRAGMA foreign_keys = ON;`.
2. تفعيل نمط الكتابة المسبقة في السجل: `PRAGMA journal_mode = WAL;` (Write-Ahead Logging) لتمكين القراءة المتزامنة دون حظر الكتابة وتحقيق أعلى استقرار للمعاملات.
3. التخزين المحلي فقط على القرص الصلب للجهاز، والتحذير الصارم من تشغيل ملف قاعدة بيانات SQLite بنمط WAL عبر مجلدات المشاركة الشبكية (Network Shares / SMB).
4. استخدام لقطات JSON داخل سجلات الفحص المعتمدة (`snapshot_json`) لحفظ الحالة التاريخية الثابتة للكاشف والمعدات والمصادر كما كانت لحظة الاعتماد.

## النموذج المرجعي (RadRiskMap)
تتبع منظومة RadRiskMap نفس الأسلوب في تشغيل قاعدة بيانات محلية آمنة مع إنشاء ملفات قفل محلية لمنع التعارض ونسخ احتياطي فوري مضغوط.

## البدائل المدروسة وأسباب استبعادها (Alternatives Considered)
1. **خوادم قواعد البيانات المركزية (PostgreSQL / MySQL):**
   - *سبب الاستبعاد:* تتطلب تشغيل خدمة خادم مستقلة، وتتطلب اتصالاً شبكياً مستمراً مع خادم قاعدة البيانات، مما يتعارض مع شرط العمل المستقل الكامل للمعامل النووية المعزولة.
2. **ملفات JSON أو Excel المستقلة:**
   - *سبب الاستبعاد:* تفتقر للسلامة المعاملاتية (ACID)، وتتعرض للتلف بسهولة عند التعديل، ولا توفر قيوداً مرجعية أو فهرسة سريعة أو حماية ضد التلاعب بسجل التدقيق.

## العواقب (Consequences)
- أداء فائق وسرعة استجابة.
- قاعدة البيانات عبارة عن ملف واحد يسهل نسخه احتياطياً وتشفيره واستعادته بالكامل.
- قيد تقني: يجب استخدامها كقاعدة محلية لجهاز واحد (انظر السؤال المفتوح 1 في `docs/OPEN_QUESTIONS.md`).
