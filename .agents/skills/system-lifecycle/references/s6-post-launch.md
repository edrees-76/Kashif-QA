# S6 — ما بعد الإطلاق

النظام المنشور يتغير بثلاثة أنواع من الطلبات، ولكل نوع مسار. أول ما تفعله
عند أي طلب: **صنّفه**، لأن الخلط بينها يحوّل إصلاحًا صغيرًا إلى إعادة بناء.

## التصنيف

| النوع | المثال | المسار |
|---|---|---|
| خطأ (Bug) | الرقم يُقرَّب خطأ | مسار الإصلاح |
| تعديل صغير (Change) | إضافة عمود لتقرير | مسار المهمة المصغّرة |
| ميزة كبيرة (Feature) | وحدة جديدة كاملة | عودة إلى S1 بنطاق محدود |

**المعيار الفاصل:** إن كان الطلب يغيّر نموذج البيانات الأساسي أو
الصلاحيات أو يضيف شاشة كاملة جديدة ← ميزة كبيرة، لا تعديل.

## مسار الإصلاح

1. البلاغ بصيغة: الخطوات ← المتوقع ← الفعلي ← صورة/سجل.
2. أعِد إنتاج الخطأ قبل الإصلاح (اطلب من المستخدم تأكيد إعادة الإنتاج).
3. برومبت إصلاح + **اختبار انحدار آلي** يمنع عودته.
4. مراجعة ← دمج (مع التذكير) ← إصدار `x.y.Z+1`.

## مسار المهمة المصغّرة (بديل plan-new-task)

لا يحتاج استجوابًا كاملًا. ثلاثة أسئلة فقط، سؤال في كل مرة:
1. ما التغيير المطلوب بالضبط، ولماذا؟
2. ما الذي قد يتأثر به (شاشات، تقارير، بيانات قائمة)؟
3. كيف ستعرف أنه نجح؟

ثم أنتج بطاقة مهمة:
```markdown
## CHG-<رقم>: <عنوان>
- السبب:
- المتطلب المتأثر: FR-xxx (أو جديد: FR-yyy)
- الملفات/الطبقات المتوقعة:
- معيار القبول:
- خطر الانحدار: ما يجب إعادة اختباره
```
ثم حلقة S3 مصغّرة، وإصدار `x.Y+1.0`.

## الدرس المستفاد (بعد كل إصدار)

اسأل المستخدم سؤالًا واحدًا: "ما أكثر خطأ أو تأخير أزعجك في هذا المشروع؟"
ثم اقترح كيف يتحول إلى:
- بند جديد في قائمة `code-reviewer` (إن كان نمط خطأ برمجي متكرر)، أو
- قاعدة في `architect-mindset` (إن كان قرار بناء)، أو
- تعديل على هذه المهارة نفسها (إن كان خللًا في العملية).
بهذا تتحسّن المنظومة التالية بأخطاء السابقة.
